# 资产分类与主机采集授权

用户补充要求（2026-11-14）：将只扫描发现的资产与自有、已授权采集的服务器等资产分开。

## 三个维度，不能用一个“已授权”布尔值混在一起

1. **资产来源**：网络发现、手动登记，未来可增加 Agent 注册。
2. **管理与业务分类**：发现待确认 / 已纳管；服务器 / 工作站 / 虚拟机 / 网络设备 / 未确认。
3. **主机采集授权**：未接入、已显式授予能力、已撤销。

允许扫描一个范围，只授权该范围内已约定的网络探测，不授权登录、读进程或安装程序。
“自己的服务器”也需要显式接入和授权采集能力。

## 任务02已实现（历史阶段）

发现快照持久化 `management_status`、`collection_access`、`asset_kind`，
默认分别为 `discovered`、`not_enrolled`、`unknown`。API 另外明确返回来源、
`hostMetrics: null` 和 `hostMetricsStatus: not_collected`，绝不填零冒充。

名称、IP、MAC、端口、VMware guestOS 提示、配置中的文字和普通备注均不能授予采集权限。
本轮没有“授权按钮”、远程凭据、Agent、主机指标上传或相关写 API。
这些字段现在是发现快照的状态，不是完整资产台账或授权管理系统。

## 任务03补充：台账关联已实现，采集授权仍未实现

已增加稳定UUID台账、人工显式关联/撤回、地址观测历史、修改版本和审计。
旧发现快照不改写；当前台账 managed 仅表示登记，不证明所有权或授予采集。
两台实验资产已登记，collectionAccess均为not_enrolled，主机指标仍null。

本轮无Agent/授权按钮，完整操作说明见《稳定资产台账-使用与接口》。

## 后续采集能力的设计约束（尚未实现）

- 稳定 UUID 台账及发现关联已经完成，IP/MAC 匹配仍不转移授权。
- 人工纳管/管理类型已可从本机CLI设置；纳管不自动获得 CPU/内存/进程权限。
- Windows/Linux 主机采集单独接入；选择 Agent 或显式远程采集后再实施。
- 分能力授权：CPU、内存、基础系统、进程清单可分别授予/撤销。
- 只读、最小权限；进程默认仅有限名称/PID/必要指标，不默认收集命令行、
  环境变量、文件、口令或登录会话。
- 绑定可验证的采集端身份，不依赖 IP/MAC 自动信任，不保存通用管理员口令。
- 认证、传输保护、令牌撤销、防重放、采集间隔与审计独立验收。
- 分别保存观测时间、新鲜度、权限不足、未接入、离线和采集错误；
  授权成功不等于采集成功，采集失败不等于主机故障。
- 吊销授权后停止接收/请求相应能力，按保留政策处理历史记录。

这项补充扩展了原先将 CPU/内存列为后续方向的计划，但不把未完成能力算成本轮成果。

## 后续字段语义需先固定（计划，不是当前可用接口）

- CPU：区分逻辑核心数与利用率；明确采样窗口、0–100% 口径，首次无基线为 null。
- 内存：总量/可用量以字节传输，使用率口径固定，缓存不能在不同平台随意混算。
- 进程：默认限量分页；PID 结合启动时间区分复用；CPU 占比口径和 RSS（驻留内存）
  单位写入契约。进程采集需独立授权，不随 CPU/内存权限自动启用。
- 每类数据分别标记未授权、未接入、等待首样本、有效、过期、权限不足和采集错误；
  这些是数据质量/接入状态，不混成一个“设备离线”。
- 不默认上传进程命令行、环境变量、完整路径或用户会话；即使授权读取进程也要限制字段。
- 前端按能力与质量状态显示“未授权/未采集/过期”，不能用 0 或绿色代替缺失值。
- 当前 API 的 hostMetrics 为固定 null 占位；真实采集接口模型实施前单独评审、
  导出新契约并更新测试/客户端，不能宣称现有结构已支持主机指标。
