# GitHub 协作交付验收（2026-11-16）

## 结论与边界

交付的是 **0.10.0 当前已实现功能的完整源码 + 精确匹配的 Windows x64 离线资源**，
不是仅能打开空页面的演示，也不是“所有规划功能已做完”的成品声明。
原运行服务/工作库未接管；新入口使用独立运行库。

已在独立的中文、空格目录，从源码候选和真正的资源 ZIP 重建：
不复制原作者 venv，不从系统 PATH 借用 Python、Node、Nmap、SSH；
安装阶段给出不可用代理，并显式使用 pip `--no-index` 和 npm `--offline`。
这证明包管理器离线重建，不等于断开整机网络或第二台实体 Windows 验证。

## 完整性与隐私

- 后端 app、原脚本、全部迁移、归档原生扫描代码、前端 src、根 scripts/tests 均逐文件盘点。
- 功能代码复制时逐字节核对；文档里的个人路径、内网地址、MAC、设备标识和主机名脱敏。
- `source-manifest.json` 列出发布快照内的所有源码文件，含原先尚未提交的种子脚本与测试。
  Git 的 CRLF/LF 转换按清单记录的规范化方式核对，不把正常换行转换误判成丢失代码。
- 发布前扫描私人配置、数据库、私钥块、GitHub token 等；命中拒绝构建候选，不打印凭据内容。
- Git 忽略规则收窄到真正运行数据目录，不再用全局 `**/data/` 吞掉未来的前端 `src/data` 模块。
- 新协作仓库从干净源码快照建立，不上传旧历史；原目录的索引、暂存整理和工作文件备份保留。
- 真实历史、账号、会话、终端操作、密钥、本机配置不上传 GitHub。
- Nmap/Npcap 不混入资源包；用户自行取得 Nmap 后可完整导入项目本地工具目录。

## 迁移过程中实际抓到并处理的问题

1. 复制旧 venv 会继续引用作者安装位置：改成官方嵌入式 Python 与项目内依赖。
2. Windows截图默认依赖系统Edge：便携模式使用匹配的 Chromium headless shell，旧模式保留兼容。
3. 旧管理脚本只认识 backend/.venv 或 .runtime/venv：增加便携预览解释器定位，保留旧部署规则。
4. 一个默认数据一致性测试暗中需要 Nmap：明确工具前提，无工具时有理由跳过，有工具时真实执行。
5. 临时 HTTP 验证只靠 PYTHONPATH：嵌入式 Python 不采用这个环境变量，改为显式选择被验证的临时源码，
   避免错误地验证原项目而误称“搬家成功”。
6. 上游只读许可文件使重复安装失败：同内容跳过复制，差异拒绝，不覆盖本地改动。
7. Windows临时解包的短暂共享锁：限定次数重试发布，不放宽路径/覆盖保护。
8. 历史Windows报告有混合编码：只对文档规范化和脱敏，程序代码不做编码改写。
9. Git换行转换影响哈希：发布清单明确文本规范化规则，代码内容变化仍能检出。
10. 真正回拉时发现一份脱敏历史文档被Windows写成双回车：增加CRLF回归用例，
    文档显式写UTF-8/LF，重建清单；不改写程序代码。
11. GitHub全新Windows运行器使用短用户名路径（如8.3别名），使两个测试的路径比较失效：
    对比较两端做同样的解析，确保注入的失败确实命中目标库，不弱化业务校验。
12. “Node 24”浮动到了新npm，暴露原锁文件兼容差异：CI与开发者入口固定本轮实测
    Node 24.11.0/npm 11.6.1，不偷偷更新前端依赖；便携资源本来就已固定相同版本。

## 协作使用

从新仓库克隆，按 `Windows协作与离线运行.md` 下载匹配资源并初始化自己的账号，
再配置自己的授权范围/设备凭据/驱动，使用 `start.cmd`。
旧 SCM 与计划任务安装功能的源代码保留，仍要求其独立部署前提，本轮没有安装这些系统任务。
原工作目录有旧历史和未完成的暂存整理，不应把它的旧分支强推到新干净仓库；
日常协作以新仓库的正常 clone 为工作目录。
